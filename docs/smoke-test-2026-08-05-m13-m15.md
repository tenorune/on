# Smoke test — M13, M14, M15 (filed and closed 2026-08-05)

Live steps for the three items closed on `claude/knockknock-unruled-decisions-ak3gaa`
and merged to `dev` at `a1d04e8`. Everything below is **jest-verified only**
until it is run here: no session container has ever held a service-account
credential, so nothing in this file has been executed by the session that wrote
it. Treat every expected value as a prediction to be falsified, not a result.

## How to read this file

**Every step has a CONTROL — a probe that must SUCCEED.** That is not ceremony.
Four steps of the previous smoke test were saved by one (A6, C5, D1, D5b): a
broken setup and a working guard look identical when the only expected outcome
is "nothing happened". If a control fails, the step proved nothing — fix the
setup and re-run it rather than recording the step as passed.

**Four traps this file is written to avoid**, three of them from the last smoke
test and the fourth found by the operator running B3 of this one:

- **Do not reuse a fixture a previous step destroyed.** The last smoke test's C4
  reused a fixture C3 had merged away. Each merge below gets its **own tag**,
  and the tags are already derived here so they cannot be improvised.
- **Nothing here asks for something unreachable by hand.** Where a claim is not
  hand-reachable it says so and says why, rather than sending you after it.
- **This app is the modular Firebase SDK.** There is no global `firebase`
  namespace; do not reach for v8 compat syntax anywhere in the browser console.
- **A number in a closure note is not a string in the UI.** B3 originally asked
  for a per-conflict path count the panel does not render, by lifting M8's
  "3 paths / 4 paths" — the totals from a canned-response harness — into a step
  as though the page printed them per conflict. Before asking an operator to
  read a value off a screen, find the line of markup that prints it.

**Preconditions.** Parts B, C and D seed **synthetic** accounts no client ever
holds, so **G3 and G6 have no author on those legs** — that is the whole reason
the merge fixture exists in the shape it does (`ops/merge-fixture.js` header).
**Part E3 uses a REAL account and G3 applies in full**: close the Mini App and
any signed-in web client for the target before touching it.

Run from `functions/`, with `$DEV` and `$PROD` set to the project ids and
`GOOGLE_APPLICATION_CREDENTIALS_JSON` holding the dev service account.

## Part A — the `--adopt` refusal (no credential, no database)

The only part of `verify-merge.js` a container without a credential can reach,
and worth running first because it is free.

**A1.** A value after the flag is refused by name:

```bash
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13a --adopt smg-m13a-shared
```

Expect a non-zero exit and:

```
Error: --adopt takes no value (got "smg-m13a-shared") — the fixture has exactly one colliding group, so this is a flag, not a list.
```

**A2 — the control.** The bare flag must be **accepted**, not refused:

```bash
unset GOOGLE_APPLICATION_CREDENTIALS_JSON
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13a --adopt
```

Expect `Error: Set GOOGLE_APPLICATION_CREDENTIALS_JSON…` — the **credential**
refusal, not an argument one. Without A2, A1 passes just as well against a CLI
that refuses `--adopt` outright, which would be a different bug.

## Part B — M13, a merge run WITH adoption (tag `m13a`)

**B1.** Seed:

```bash
node ops/seed-merge-fixture.js --project $DEV --prod-project $PROD --tag m13a --yes
```

**B2 — the control on the seed.** Refresh the panel, run the integrity report.
Expect **exactly one `auth-missing` INFO per seeded uid** and **nothing above
INFO**. The seed is self-consistent by construction, so anything else here is
the seed failing, and every later step would be reading a tree that is not the
one these claims describe.

**B3.** Merge `smk-m13a-loser` → `smk-m13a-survivor` through the panel, and
**TICK the shared group's adoption** in the preview dialog. Before approving,
watch **two** things change and one of them is a number:

1. **The conflict's resolution flips.** In the conflicts block — and in the
   tick-box's own label, which renders the same `detail → resolution` string —
   the line reads:

   ```
   group-member-collision: both accounts are members of smoke shared group: "L in GB" vs "S in GB" → survivor's record kept
   ```

   unticked, and `→ loser's displayName adopted` ticked. Unticking must put it
   back. Seeing it move in *both* places is expected: `adoptBlock` reuses the
   same string, it is one fact rendered twice.

2. **The write-set footnote gains exactly one path.** `N paths in the preview
   write-set` must read **53** unticked and **54** ticked, for this fixture.
   The path the tick adds is precisely the one B5 goes on to check:
   `groups/smg-m13a-shared/members/smk-m13a-survivor/displayName`.

This is the precondition for B4 meaning anything — if the tick does not change
the plan, there is nothing for `--adopt` to describe.

⚠️ **53/54 are derived from the code at `a1d04e8`, not observed**, and they are
the totals for a **plain** fixture at this tag: `--telegram` seeds more paths
and both numbers move. What must hold regardless of the totals is the
**difference of exactly one**, and that it is that path.

⚠️ **An earlier draft of this step asked for "4 paths" ticked and "3" unticked,
and the panel shows no such thing.** Those were M8's numbers from a
canned-response browser harness whose whole write-set was three paths — a total,
read here as though it were a per-conflict count. The panel has never rendered a
count beside a conflict. Corrected on the operator's report from the live panel,
which is the fourth time this repo has caught a written prescription describing
something the code does not do.

**B4.** Read it back **with** the flag:

```bash
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13a --adopt
```

Expect `ALL 57 CLAIMS HOLD.` and `adopt=yes` on the header line.

**B5 — the control, and the actual M13 observation.** Re-run against the **same**
tree **without** the flag:

```bash
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13a
```

This must **FAIL**, with exactly one claim owed:

```
1 OF 57 CLAIM(S) OWED:
  ✗ groups/smg-m13a-shared/members/smk-m13a-survivor/displayName — want "S in GB", got "L in GB"
```

…and the failure block must now name the cause:

```
• the shared group's adoption tick — if the ONLY owed claim is that group's displayName
  and the value it got is the LOSER's per-group name, the merge is correct and this run
  was told the wrong thing: re-run with --adopt (M13).
```

⚠️ **If B4 passes and B5 also passes, B4 passed for the wrong reason** — the flag
is being ignored and both runs are reading the same claims. That is the failure
mode this pair exists to catch, and it is exactly what M13 was.

**The count of one is load-bearing.** It is what tells M13 apart from a merge
defect: the tick moved precisely the record it should and nothing else. Two or
more owed claims here is a different finding and does **not** close this step.

**B6.** Clean up:

```bash
node ops/seed-merge-fixture.js --project $DEV --prod-project $PROD --tag m13a --clean --yes
```

## Part C — M13, a merge run WITHOUT adoption (tag `m13b`)

⚠️ **A NEW TAG. Part B merged `m13a` away and then deleted it** — reusing it here
is the mistake the last smoke test made at C4.

**C1.** Seed `m13b`, same command shape as B1.

**C2.** Merge `smk-m13b-loser` → `smk-m13b-survivor`, **leaving the adoption tick
alone**. The resolution must read `→ survivor's record kept`, and the write-set
footnote must show the **lower** of the two counts from B3 — the un-adopted
plan. Do not tick anything here.

**C3.** Read it back with **no** flag:

```bash
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13b
```

Expect `ALL 57 CLAIMS HOLD.` and `adopt=no`. This is the half that proves the
default did not flip — the cheap failure mode of a change like this is making
the *new* case pass by breaking the old one.

**C4 — the control, the mirror of B5.** Re-run **with** `--adopt`:

```bash
node ops/verify-merge.js --project $DEV --prod-project $PROD --tag m13b --adopt
```

This must **FAIL** with exactly one claim owed — the same path, values reversed:

```
✗ groups/smg-m13b-shared/members/smk-m13b-survivor/displayName — want "L in GB", got "S in GB"
```

Together with B5 this is what proves the flag **selects** an expectation rather
than merely relaxing one. A flag that made both runs pass would satisfy B4 and
C3 and be worthless.

**C5.** Clean up `m13b`.

## Part D — M14, the seeded charset (tag `m14a`)

⚠️ **DO NOT RUN `verify-merge.js` IN THIS PART, AND DO NOT MERGE.** M14 is a
property of the **seed**, so this fixture is seeded and then read where it
stands. `verify-merge.js` is the **post-merge** read-back: its 57 claims
describe a tree where the merge has already run, so against a freshly seeded
fixture it correctly reports most of them owed (`want "SMKM14AF1", got null` —
the contact has not carried because nothing has carried). That is the tool
working, not a finding. An earlier draft of D1 called it anyway; see the note at
the end of this part.

**D1.** Seed `m14a`:

```bash
node ops/seed-merge-fixture.js --project $DEV --prod-project $PROD --tag m14a --yes
```

**D2 — read the codes off the panel.** Refresh it, users tab, and type
`smk-m14a` into the filter box. Six rows, and the **`code`** column must read:

```
SMKM14AL  SMKM14AS  SMKM14AP1  SMKM14AP2  SMKM14AF1  SMKM14AC1
```

All upper-case, all matching `^[A-Z0-9]{1,32}$`. Under the pre-M14 build these
would have been `SMKm14aL` and friends — a state no client could have written,
because SEC-1 has forbidden it since 2026-08-04.

*Control:* clear the filter and type **`SMKM14A`** instead — the code, not the
uid. The **same six rows** must come back, because the filter matches either
field. That is what tells "the codes really are these strings" from "the table
is stale or the seed did not land"; if the second filter returns nothing while
the first returns six, you are reading a cached page.

**D3 — the codeIndex check, from the tool built for it.** Run the integrity
report. `integrity.js` already asserts the property this step wants: for every
account, `codeIndex/{presence.code}` must point back at that uid, and it raises
**`code-index-missing`** at **ERROR** severity when it does not.

Expect **no `code-index-missing`** naming any `smk-m14a-*` uid.

*Control:* the report must show **exactly one `auth-missing` INFO per seeded
uid** — six of them — **and nothing above INFO**. Those INFOs are the proof the
report actually looked at these accounts. A report with no findings at all
against six freshly seeded synthetic accounts means it did not run, and "no
errors" would then be worth nothing.

**D4 — the strand signature.** In the same report, expect **no
`code-index-dangling`** warnings. That check fires when an index entry resolves
to a uid with no user record, which is *exactly* what a stranded pre-M14 code
looks like. On a project whose old fixtures were cleaned before this change
landed, there should be none anywhere — not just none for this tag.

**D5 — clean, and prove the index went with it:**

```bash
node ops/seed-merge-fixture.js --project $DEV --prod-project $PROD --tag m14a --clean --yes
```

Then re-run the integrity report. Expect the six `auth-missing` INFOs to be
**gone** (the accounts no longer exist) and **still no `code-index-dangling`**.

That pairing is the whole point: if `--clean` nulled the accounts but left their
`codeIndex/` entries behind — the M14 strand hazard, which is what happens when
the codes are derived one way and cleaned another — the six INFOs would vanish
and **six `code-index-dangling` warnings would appear in their place**. Their
absence is only meaningful because D3 established the entries existed and
resolved correctly a moment earlier.

⚠️ **What this part does NOT and CANNOT establish.** M14's actual claim is
*realism* — that the fixture writes a state a client could have produced. Proving
that needs a rules-validated write **as one of those uids**, and the fixture
accounts are synthetic with no Auth record (that is the `auth-missing` INFO in
B2), so no ID token for them exists or can be minted by hand. The charset is
pinned against the shipped rules in
`functions/test/ops-merge-fixture-rules.test.js` instead, which parses
`database.rules.json` rather than restating it. **Do not go looking for a live
version of that check** — this is the same shape as the last smoke test's D5,
which sent a session after something unreachable.

⚠️ **An earlier draft of D1 ran `verify-merge.js` against the un-merged
fixture** to list the seeded codes, and it reported most of its 57 claims owed —
correctly, since the merge had not run. `verify-merge.js` answers one question
("did the merge leave the tree it should?") and cannot be repurposed into a
node reader. The right instruments were already in the repo and are what this
part now uses: the panel's `code` column for the values, and `integrity.js`'s
`code-index-missing` / `code-index-dangling` for the index. Corrected on the
operator's report from a live run. **The lesson is the same one B3 carries** —
reaching for a familiar tool is not the same as checking it answers the question
being asked.

⚠️ **The strand hazard is not re-testable once it is gone.** A pre-M14 fixture
must be cleaned by a pre-M14 build, because `--clean` derives the keys it nulls
from `fixtureCodes`. The old fixtures were reported cleaned before the merge, so
there is nothing left on dev to reproduce it against — and creating one would
mean checking out the old build to seed. Not worth it; the constraint is
recorded at the function and in `ops/README.md`.

## Part E — M15, the panel column (no fixture)

**E1.** Open the panel, users tab. The column header must read **`auth created`**,
and hovering it must show the tooltip naming the Auth record as its source and
the expunge/re-bootstrap divergence.

*Control:* the neighbouring header still reads **`last active`**. If the whole
row of headers is wrong you are looking at a stale page — hard-refresh; the
panel is served from disk by a local server and a cached page is the likeliest
false result here.

**E2.** Click the `auth created` header. Rows must **reorder by that value**.

*Control:* click `last active` and confirm the rows reorder **differently**. The
failure mode a rename introduces is a header whose `data-k` no longer matches
any row field — the column then looks right and silently stops sorting. If
neither column sorts, the page is broken rather than the column.

**E3 — the divergence itself, and the reason M15 was filed.** Optional, and
**destructive**: use a throwaway Telegram-linked account, never a real one.

1. Note its `auth created` and `last active` values.
2. Expunge its RTDB data (this leaves the Auth record standing — that is the
   whole point).
3. Re-open the Mini App as that account so it re-bootstraps onto the **same**
   deterministic uid.
4. Re-read the row: `last active` is now seconds old while `auth created` still
   reads **days**.

The step passes when that divergence is **self-explaining** — the label says
`auth created`, the tooltip says why — rather than when the numbers agree. They
are supposed to disagree. Under the old label that disagreement read as a bug in
the table; that misreading is what M15 fixed, and route (b), showing a real
RTDB-derived created time beside it, was rejected because **no such field
exists**.

⚠️ G3 applies here and nowhere else in this file: close every client for the
target account first, or a still-live session republishes its cache into the
nodes the expunge just cleared.

## What a complete run settles, and what it does not

**Settles:** that `--adopt` selects the right expectation in both directions on
live data (B4+B5+C3+C4); that the panel's tick still changes the plan (B3); that
seeded codes satisfy the shipped charset on a real project and that `--clean`
takes their index entries with them (D1–D4); and that the renamed column reads
correctly and still sorts (E1–E2).

**Does not settle:** that a client could actually write those codes (not
hand-reachable — see D's note); that the read-back's other 56 claims are right,
which is the merge leg's own business and unchanged by this work; or anything
about the five WON'T FIX items or G3/#302, which this session did not touch.

**Nothing here has been run.** Every expected string above is derived from the
code as merged at `a1d04e8`, and the two CLI refusals in Part A are the only
ones this session executed — with no credential, against no project.
