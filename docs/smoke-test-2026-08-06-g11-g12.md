## How to read this file

**Every step has a CONTROL — a probe that must SUCCEED.** A guard that refuses
everything is indistinguishable from a correct guard, and only the control tells
them apart. Two of the results below are load-bearing *because* their control
passed, not because their guard fired.

## Part A — G11, the `codeIndex` rule

Two ordinary web accounts on dev: **A** (attacker) and **V** (victim, holding an
advertised code). No Telegram, no admin credential.

**Probe route.** No `window` handle exists, so the rules were driven through the
RTDB REST API with a real ID token lifted from a signed-in tab's IndexedDB
(`firebaseLocalStorageDb` → `firebaseLocalStorage` → the
`firebase:authUser:` row → `value.stsTokenManager.accessToken`), then
`curl "$DB/<path>.json?auth=$TOK"`. `TOK` and `AUID` must come from the **same**
tab: the write rule is `newData.val() === auth.uid`, so a mismatched pair fails
probe A1 in a way that looks exactly like a guard firing.

| # | probe | expected | result |
|---|---|---|---|
| A1 | **CONTROL** — A claims a free code | 200 | ✅ |
| A2 | **CONTROL** — A re-asserts the entry it now holds (the rotate/retry path the fix preserves) | 200 | ✅ |
| A3 | **GUARD** — A repoints V's live entry at itself | 401 `Permission denied` | ✅ |
| A4 | **GUARD** — A deletes an entry it does not own | 401 `Permission denied` | ✅ |

A1 is what makes A3/A4 mean anything: an expired ID token also returns 401. With
A1 green the token is known good, so a later 401 is a real refusal. That is
cheaper and more reliable than matching error strings.

## Part B — G11, the `lookupCode` cross-check

The rule refuses *new* takeovers but **cannot un-hijack an entry taken over
before it shipped**, which is why the fix has a client half at all. A1 left
exactly the right condition behind: `codeIndex/QQQQQQ → A` while A advertises a
different `presence/code` — a disagreement created by a route the rules permit.

| # | probe | expected | result |
|---|---|---|---|
| B1 | **GUARD** — V types `QQQQQQ` into add-person | `Code not found. Check the code and try again.` and **no follow created** | ✅ |
| B2 | **CONTROL** — V types A's real advertised code | A added normally | ✅ |

Without the cross-check B1 would have returned A's uid and V would have silently
followed the attacker — the entire payoff of the hijack.

⚠️ **Two short-circuits will make either step prove nothing** and are not
defects: an account already following the target gets
`You're already following …` before `lookupCode` is called, and A's own browser
gets `That's your own code.` on its advertised code. Run both from V.

## Part C — G12 sink 4, the `buildMergePlan` repoint

Fixture seeded by the operator:

```bash
node ops/seed-merge-fixture.js --project $DEV --prod-project $PROD \
  --tag g12a --telegram --yes
```

Which yields loser `smk-g12a-loser`, survivor `smk-g12a-survivor`, peer
`smk-g12a-peer1`, and one genuine token `smt-g12a-loserinvite`.

**Two entries were then planted with the Admin SDK.** The guard under test lives
in the *function*, not the rules, so planting by admin is legitimate and does
not weaken the test — it stands in for what a holder can do through the
rules-permitted path, since the rules constrain nothing about keys under
`users/$uid/invites`.

| planted | shape | role |
|---|---|---|
| `smt-g12a-victimtoken` | index entry owned by **peer1**, record planted under the **loser** | GUARD |
| `smt-g12a-legacytoken` | index entry is a **legacy bare uid STRING** equal to the loser | CONTROL |

| # | probe | expected | result |
|---|---|---|---|
| C1 | **GUARD, preview** — the conflicts block names the planted token | `invite-index-unowned: … resolves to smk-g12a-peer1 → index left where it points; the loser record still moves to the survivor` | ✅ **RENDERED** |
| C2 | **GUARD, post-execute** — victim entry unchanged | still `ownerUid: smk-g12a-peer1` | ✅ |
| C3 | **CONTROL** — the loser's genuine token | repointed, `ownerUid` = survivor | ✅ |
| C4 | **CONTROL** — the legacy bare-string entry | rewritten to full `{scope,ownerPath,ownerUid}`, `ownerUid` = survivor | ✅ |
| C5 | **CONTROL** — `verify-merge.js --tag g12a --telegram` | all claims hold | ✅ **61/61** |

**C1 and C2 are separate claims and both were required.** `ops/merge.js` makes
reporting an explicit requirement, not a side effect — *"a refused repoint is
REPORTED, not skipped silently: the operator is the only thing standing between
this plan and a destructive write"* — the same reasoning G4 applies to cascades.
A read-back alone would have shown a working-but-silent guard as a pass.

**C4 is the one to keep.** That branch read `.ownerUid` off an entry that can be
a legacy bare **string**, which would have permanently stranded every legacy
token its real owner tried to move. It passed all four of its own targeted tests
and was caught only by `telegram-auth.test.js:583`, a pre-existing test in an
untouched file. It has now converted correctly on live data.

**C5 also settles a prediction**: the planted tokens did not perturb the
verifier's claim set, so the guard refused one repoint without collateral damage
to the merge.

## Part D — G12 sinks 1–3, behind the Telegram callables

`graduateTelegram` and `unlinkTelegram` authenticate with
`requireTelegramUser`, which verifies an **HMAC over the bot token** — Firebase
auth reaches neither. Rather than a phone and the real Mini App, initData was
**minted with the dev bot token** and the callables were called over plain
HTTPS (`https://europe-west1-on-on-22cb4.cloudfunctions.net/<name>`, body
`{"data":{…}}`).

Three things made this far cheaper than it looks, and are the reusable part:

- **`TELEGRAM_UID_SECRET` is not needed.** Let `validateTelegram` bootstrap the
  account, then read `derivedUid` back out of `telegramUsers/{tgId}`. Only the
  bot token is required.
- **Each callable consumes the derived account** (both graduate and unlink
  expunge it), so each sink used its **own synthetic `tgId`** — no ordering
  hazard between them.
- **`normalizeRecoveryCode` validates format only**, not membership of the
  wordlist. A nonsense phrase is therefore both legal and guaranteed to leave the
  target uid free, which `graduateTelegram` requires.

| # | probe | expected | result |
|---|---|---|---|
| D1 | **GUARD** (sink 1) — victim's token planted under the derived account | not repointed | ✅ still `ownerUid: g12b-victim` |
| D2 | **CONTROL** (sink 1) — the account's own token | repointed to the graduated uid | ✅ |
| D3 | **CONTROL** (sink 1) — a legacy bare-uid **STRING** entry | rewritten to full object shape | ✅ |
| D4 | **GUARD** (sink 2) — planted victim token | survives | ✅ |
| D5 | **CONTROL** (sink 2) — own token, and a legacy string entry | both released | ✅ `null` |
| D6 | **GUARD** (sink 3) — victim token planted under an owned group | survives | ✅ |
| D7 | **CONTROL** (sink 3) — a group token owned by **another member** | released anyway | ✅ present before, `null` after |

**D2/D3 are self-evidencing and D7 is not — that distinction cost a run.** The
graduated uid came back as `8456899437bf8a59e68c8389585763d0`, which
independently equals `sha256('zzsmoke-zzalpha-zzbeta-zzgamma')[:32]`: a value
that specific can only have come from the repoint, so it proves the destination
was the *expected* account rather than merely a different one.

⚠️ **A release-type control cannot work that way, and the first sink-3 run did
not notice.** Its pass condition is "`null` afterwards", which is
indistinguishable from "never planted in the first place" — so a guard that
released *nothing* would have produced identical output. Sinks 1 and 2 survived
that gap on independent evidence (sink 1's controls self-evidence, and sink 2's
seeding uses byte-identical code), but **sink 3's control was not established
until it was re-run with a check BEFORE the fire.** It then showed the group
token present with `ownerUid: g12b-member`, and `null` after.

**The generalisation: for a guard whose correct behaviour is a DELETE, the
control must be observed existing first.** After-only is not evidence. This is
the same shape as the prescriptions the roadmap keeps recording — the
procedure was written from the code path without asking what its own null would
prove.

Second-order: the helper's `--check` printed every token name regardless of
which sink created it, so several rows read `null (released)` for entries that
never existed. Harmless here, but it is what made the sink-3 ambiguity easy to
miss — **a reporting tool that cannot distinguish absent from removed will hide
exactly this class of gap.**

## What this does NOT establish

- **G11's pre-fix behaviour.** Probe A3 now refuses the overwrite, so the chain
  was watched dying at its second step rather than observed working. Confirming
  the original takeover would mean reverting the rule on dev.
- **Anything about prod.** This ran on `on-on-22cb4` only. Every guard here is a
  rules or functions behaviour that prod does not have until `dev` → `main`.
- **Durability.** One run per sink, one fixture shape per sink. Seen is not
  proven.

## Reusable, from the friction rather than the results

- **An empty shell variable reads as a security failure.**
  `curl "$DB/codeIndex/$VCODE.json"` with `VCODE` unset collapses to
  `$DB/codeIndex/.json` — a read of the **whole** node. `.read` is granted at
  `$code`, one level down, so the answer is `Permission denied`, identical to a
  rejected token. It cost two rounds of chasing the token. **The discriminator:
  read a key that definitely does not exist** — `null` + 200 proves auth is fine
  and the fault is the path. Echo variables in brackets, `[$VCODE]`, so empty is
  visible.
- **`copy()` is unavailable in a snippet containing top-level `await`.** Chrome
  wraps such input in an async function and does not inject the Command Line API.
  Stash to `window.__tok`, then run `copy(__tok)` as a separate command.
- **`export UID=…` fails in zsh** — `UID` is a readonly special. Any probe
  variable named after a shell builtin will do this.
- **ESM resolves bare specifiers from the importing file's location, not the
  cwd.** A helper script in `/tmp` cannot see `functions/node_modules` however
  you set the cwd; it has to live under `functions/`.
