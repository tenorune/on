1. Overview

The app lets users set an availability status (available/unavailable with a timeout) and personalise how they appear via a status color and optional UI theme.

Color and theme are configured through a Palette Picker — a row of swatches organised into two independent sets (Natural and Electric, 8 palettes each). Each palette provides a primary status color, a full UI theme (8 CSS variables), and 7 complement colors. Users can also save and restore previous configurations through the Favorites Strip.

Other users see these choices reflected on User Cards in the following list, and can adopt another user's color+theme combo via long-press.

2. Feature Flags

Two flags gate palette and strip behaviour. Both are compile-time constants in js/features.js.

Flag Default What It Gates
PALETTES_ENABLED true Swatch row rendering, theme CSS variables, palette-colored status dots, palette-styled user cards, status color persistence to Firebase. When false: default green status dot, no swatch row, no card theming.
PALETTE_INTERACTIONS_ENABLED true Favorites strip (cross-device history pills), saveCombo history recording, long-press adoption on user cards. Requires PALETTES_ENABLED = true. When false: no strip, no adoption, no history.
KNOCK_ENABLED true Tap-to-knock on mutual cards (sends a notification). When false: no tap handler on cards.
CALL_ENABLED true Swipe-right-to-call on mutual cards (enters call mode with glow animation). When false: no swipe handler on cards.
Flag notation: Throughout this document, PALETTES marks features gated by PALETTES_ENABLED and INTERACTIONS marks those additionally gated by PALETTE_INTERACTIONS_ENABLED.

3. What the User Sees

3.1 Status Color

The status color is a hex color (e.g. #22c55e) that represents the user's current visual identity. It is displayed as:

  • The user's own status dot (background + box-shadow glow)
  • The left border accent on other users' cards
  • The "Available for …" text color on cards
  • The dot color on other users' following list entries

Status color defaults to #22c55e (green) and changes when the user taps a swatch, taps a complement, adopts from a card, or restores from history.

3.2 UI Theme

A UI theme is a set of 8 CSS color variables that re-skin the app's background, surfaces, text, and accent. A theme is activated by double-tapping a palette swatch ("entering palette mode"). In base mode (single tap or no palette mode), only the status color changes; the UI stays on the default dark-slate theme.

ModeStatus ColorUI ThemeFirebase paletteKey
Base mode Palette's primary color Default (slate) null
Palette mode Primary or any complement Palette's theme e.g. "forest"
Why null and not "slate"? Slate is not a palette — it is the hardcoded CSS default (the :root values in app.css). The 16 palettes in PALETTE_SETS each define a unique theme, complements array, and glow color. Slate has none of these; it is simply what the UI reverts to when resetThemeVars() is called. Using null signals "no palette chosen" rather than implying slate is a selectable entry in PALETTE_SETS.

3.3 User Cards (Followee View) PALETTES

When a followed user is available, their card reflects their status color and (if present) their palette theme:

Card ElementData SourceBehaviour
Status dot userData.statusColor Background, border, and glow set to status color when available; cleared when unavailable
"Available for …" span userData.statusColor Inline style="color:${color}" on the <span>. Always applied when available, regardless of paletteKey. In palette mode this is overridden to palette.color.
Card background userData.paletteKey → palette.theme.surface Dark-tinted surface from palette theme. Only if paletteKey is set and user is available. In base mode (paletteKey = null): cleared, falls back to CSS default.
Left border userData.statusColor or palette.color Accent stripe. In palette mode: palette.color (primary). In base mode: statusColor when available, cleared when unavailable.
Status text color palette.theme.textMuted or CSS default Palette mode (paletteKey set): statusEl.style.color is set to palette.theme.textMuted.
Base mode (paletteKey = null): statusEl.style.color is cleared (''), so the text falls back to inherited CSS (var(--text) or the card's default rule). The "Available for …" <span> still shows the status color via its own inline style, but the surrounding text (e.g. "Last seen") uses the CSS cascade, not textMuted.

When paletteKey is null or the user is unavailable, all palette-specific card styling (background, border, text color) is cleared. The card reverts to CSS defaults, though the "Available for …" span retains its inline statusColor.

3.4 Palette Picker PALETTES

The palette picker is a horizontal swatch row visible when the user is unavailable (hidden when available). It has two rendering modes:

Base Mode (no active theme)

  • Shows 8 swatches for the active set (colored circles)
  • The swatch matching selectedKey has a white ring (.selected)
  • A toggle button (Bolt/Flower icon) switches between Set 1 and Set 2
  • First tap on a swatch: changes status color, updates selectedKey
  • Second tap on the selected swatch: enters palette mode

Palette Mode (theme active)

  • Shows the key swatch (palette's primary color) at its original index position
  • Shows 7 complement swatches (derived colors) filling the remaining positions
  • White ring on whichever swatch matches selectedColor
  • Tapping a complement: changes status color only; theme stays
  • Tapping the key swatch when it's already selected: exits palette mode
  • Tapping the key swatch when a complement is selected: reverts status to primary color

3.5 Favorites Strip INTERACTIONS

A horizontally-scrollable strip below the swatch row. It is a pure history list of recently-used color/theme combos — most recent first, capped at MAX_FAVORITES = 8.

Changed since v0.7: the strip no longer has "slot" pills (the two always-present pills that mirrored Set 1 / Set 2). Every pill is now a history combo, and the favorites array is synced across devices via userPrefs/{uid}/favorites (a sibling device's change re-renders the strip through the favorites-synced event).

History Pills

  • Auto-saved combos, most recent first, capped at 8
  • Each pill is a split circle: left half = statusColor, right half = surface2
  • Full opacity, tappable. Created by a single writer, saveCombo(combo), called when the user goes available (buildDirectCombo()) or long-press-adopts another user's combo (buildAdoptedCombo()) — in both Direct and group context
  • The whole array is deduped by visual identity (statusColor + surface2) on every write (see §6)

Tapping a Pill

  • In Direct: restores the live picker to that combo (set, swatch, color, theme) without mutating history
  • In a group: applies the combo to the group's statusOverride + per-group palette state (same path as long-press group adoption), via applyAdoptedComboInGroup

Dual containers

The strip is rendered into two DOM nodes — #favorites-strip (inside #main-ui-direct) and #group-favorites-strip (inside #group-context-root). Both show the same favorites; only the one in the active context is visible. Click handlers dispatch by whichever context is active at tap time.

Layout

Pills stretch dynamically to fill the strip width rather than using a fixed width. With up to 8 pills sharing the space, each pill shrinks or grows proportionally (animated on count change).

Collapsed Mode

A single gradient line showing all pill colors left-to-right. Tap to expand. A first-use "peek" animation (every 6s until opened) nudges the user to open it. Collapsed/expanded state is itself synced (userPrefs/{uid}/favoritesCollapsed).

Gestures

  • Swipe down near the collapsed strip or the gap below it: expands to full pill view
  • Swipe up below the expanded strip: collapses to gradient line
  • overscroll-behavior-y: none on html, body prevents iOS Safari pull-to-refresh from interfering with the swipe-down gesture

4. Data Model

4.1 Firebase Schema

Firebase Realtime Database. The user's palette fields live on the presence record at users/{userId}/presence/. Call signaling, revocations, and knocks are separate top-level mailboxes (not sub-nodes of the user record).

users/
  {userId}/
    presence/
      code: string               // 6-char discovery code
      status: "available" | "unavailable"
      availableUntil: number|null  // ms timestamp
      lastSeen: number             // ms timestamp
      statusColor: string          // hex, e.g. "#22c55e"
      paletteKey: string|null      // active palette ID or null (base mode)
    followers/
      {followerId}: string         // follower's code

calls/                             // symmetric call mailboxes (was the old callState field)
  {userId}: { to|from, ts, answered? } | null
revocations/                       // "X removed me as a follower" mailbox (was revokedFollowers)
  {userId}/
    {revokerId}: true
knocks/
  {recipientId}/
    {senderId}: { count, ts }
Per-audience palette (groups): a member's per-group color/theme override lives at groups/{groupId}/members/{memberUid}/statusOverride = { enabled, status, availableUntil, statusColor?, paletteKey? }. When enabled, that group renders the member with the override's color/theme instead of their Direct statusColor/paletteKey — this is the "per-audience color picker" the group swatch row drives.

Palette-Relevant Fields

FieldTypeWritten ByPurpose
statusColor hex string palettes.js, favorites.js, following.js Current status indicator color. Read by peers via watchPresence to style cards.
paletteKey string | null palettes.js, favorites.js Active palette theme ID (e.g. "forest", "volt"). Peers look up the palette object to apply card theming. null = base mode (no theme).
Dual storage pattern: Both statusColor and paletteKey are always written together. A peer reads paletteKey to get the theme and statusColor for the exact color (which may be a complement, not the palette's primary).

Firebase Read/Write Operations

FunctionFileTypeWhat It Does
setStatusColor(userId, color) db.js Write Updates statusColor field
setPaletteKey(userId, key) db.js Write Updates paletteKey field (string or null)
setStatus(userId, status, availableUntil) db/social.js Write Updates presence/status + presence/availableUntil (lastSeen is bumped separately by touchLastSeen)
watchPresence(userId, callback) db/social.js Stream Real-time listener on users/{userId}/presence; delivers statusColor and paletteKey to peers

The db.js entries in the tables throughout this doc now resolve through the db/{social,groups,canvas}.js split — see §9. The public ./db.js import path is unchanged (it re-exports the three modules), so call sites and the function names above are the same.

4.2 Local Palette State

Managed by getPaletteState() / setPaletteState() in prefs.js. Reads stay synchronous off a localStorage cache (key statusapp_palette_state, the underlying store still lives in store.js); writes also fan out to userPrefs/{uid}/paletteState/direct so the Direct picker state syncs across devices.

Per-group palette state: each group keeps its own independent picker state at userPrefs/{uid}/perGroup/{groupId}/paletteState, via getGroupPaletteState(groupId) / setGroupPaletteState(groupId, state) (same shape as below). The group swatch row reads/writes this instead of the Direct state. 
{
  activeSet: 1 | 2,                   // Which set is currently active
  sets: {
    "1": {
      selectedKey: string,             // Palette key shown as selected (e.g. "forest")
      activePaletteKey: string | null, // null = base mode; string = palette mode
      selectedColor: string | undefined // Explicit color choice; set on user action only
    },
    "2": {
      selectedKey: string,             // e.g. "volt"
      activePaletteKey: string | null,
      selectedColor: string | undefined
    }
  }
}

Field Purposes

FieldSet OnRead ByPurpose
activeSet Set switch, adoption, history restore Swatch rendering, strip rendering, buildDirectCombo Which set (1 or 2) the user is currently working in
selectedKey First swatch tap, adoption, history restore renderSwatchRow (white ring position), switchSet (color lookup) Which palette within the set is selected
activePaletteKey Second swatch tap (enter), key swatch tap (exit), adoption renderSwatchRow (base vs palette mode), switchSet (theme apply/reset) null = base mode (color only). Non-null = palette mode (color + full theme)
selectedColor Every explicit user color choice (swatch tap, complement tap, key swatch select, adoption) renderSwatchRow (ring on complement), switchSet (restore color), buildDirectCombo (combo color) The exact color the user chose. May differ from the palette's primary when a complement is selected. buildDirectCombo reads it (falling back to --my-status) when assembling the combo that going-available saves.
Picker state vs. peer-visible state: selectedKey, activePaletteKey, selectedColor, and activeSet are picker state — cached in localStorage and synced privately to userPrefs/{uid}/paletteState/direct (cross-device, not visible to peers). Only statusColor and paletteKey are written to the public presence record for peer visibility.

4.3 Favorites Storage

Array of "combo" objects, capped at MAX_FAVORITES = 8. Managed by getFavorites() / setFavorites() in prefs.js: reads come from a localStorage cache (key statusapp_favorites), and writes also fan out to userPrefs/{uid}/favorites so the strip syncs across devices.

Combo Object Shape

{
  statusColor: string,       // hex — the status indicator color
  surface: string,           // hex — card bg (palette.theme.surface or DEFAULT_SURFACE)
  surface2: string,          // hex — pill right-half (palette.theme.surface2 or DEFAULT_SURFACE2)
  paletteKey: string | null, // palette ID or null (base mode)
  selectedKey: string,       // palette key within the set
  activeSet: 1 | 2           // which set this combo belonged to
}
FieldSourceUsed For
statusColor CSS --my-status (buildDirectCombo) or the adopted source's color (buildAdoptedCombo) Left half of pill color; pen color for Call Canvas; restored on tap
surface palette.theme.surface or DEFAULT_SURFACE (#1e293b) Card background color; canvas background color for Call Canvas
surface2 palette.theme.surface2 or DEFAULT_SURFACE2 (#334155) Right half of pill color; visual hint of theme
paletteKey activePaletteKey from palette state Restored on tap to re-enter palette mode (or null for base mode)
selectedKey selectedKey from palette state Determines which swatch gets the ring after restore
activeSet activeSet from palette state Which set to switch to on restore

Default Constants

When a combo has no active palette (paletteKey: null, base mode), derived fields fall back to these constants defined in favorites.js:

ConstantValueUsed As Fallback For

DEFAULT_SURFACE #1e293b surface — the default slate card background (--surface)

Removed since v0.7: the slot model is gone, and with it the in-memory _lastCommittedCombo baseline, slotCombo(), and handleSlotTap(). Saving is now a single stateless writer (saveCombo) plus whole-array dedup, so no "previous combo" bookkeeping is needed.

5.2 Complement Swatch Tap (in Palette Mode)

User taps complement swatch [color] (while in palette mode)
  |
  v
Complement click handler
  |

  +-- CSS: --my-status = color
  +-- setStatusColor(userId, color)       <-- Firebase (color only, theme stays)

  +-- setPaletteState(state)              <-- localStorage

The theme (paletteKey) does not change — only the status color within that theme changes. This is how a user can have Forest theme with a non-Forest status color.

5.3 Set Switch

Triggered by:

  • The Bolt/Flower toggle button in the swatch row
  • History pill restore (Direct) — handleHistoryTap calls switchSet(combo.activeSet) to land on the pill's set
  • Long-press adoption — if the adopted combo belongs to the user's currently inactive set, applyAdoption sets activeSet to that set before calling enterPaletteMode or switchSet, effectively switching sets as a side effect
switchSet(toSet, userId)
  |
  +-- state.activeSet = toSet
  +-- setPaletteState(state)                       <-- localStorage
  |
  +-- Read target set's stored state:
  |     selectedKey, activePaletteKey, selectedColor
  |
  +-- Determine statusColor:
  |     selectedColor || getPaletteByKey(selectedKey).color
  |
  +-- CSS: --my-status = statusColor
  +-- CSS: --my-glow = getGlowForColor(statusColor)
  +-- setStatusColor(userId, statusColor)           <-- Firebase
  |
  +-- if activePaletteKey:
  |     applyThemeVars(palette.theme)               <-- CSS: 8 theme vars
  |     setPaletteKey(userId, activePaletteKey)      <-- Firebase
  +-- else:
  |     resetThemeVars()                             <-- CSS: slate defaults
  |     setPaletteKey(userId, null)                   <-- Firebase
  |
  +-- renderSwatchRow(userId)
       +-- dispatch 'palette-state-changed'
Set independence: Each set stores its own selectedKey, activePaletteKey, and selectedColor independently. Switching sets restores the target set's full state without affecting the other set.

5.4 Going Available INTERACTIONS

User taps dot to go available
  |
  v
setAvailable(availableUntil) in me.js
  |
  +-- if transitioning from unavailable & PALETTES_ENABLED:
        |
        v
      saveCombo(buildDirectCombo())          <-- save the combo you're going available WITH
        |
        +-- Guard: PALETTES && INTERACTIONS?  <-- no = return
        +-- prepend combo to getFavorites()
        +-- dedupeCombos(whole array)         <-- drop visual dups (statusColor+surface2)

Unlike v0.7 (which saved the previous combo via a _lastCommittedCombo baseline), going available now simply saves the combo you are going available with. saveCombo's whole-array dedup means re-going-available with an unchanged combo is a no-op (it already sits at the head), so there is no separate "no change" guard to maintain.

  |                                                BEFORE applying (apply mutates picker state).
  |                                                Whole-array dedup handles same-combo adoption.
  |

        |

        |

        |     --my-status = statusColor
        |     --my-glow = glow

        |     Update state: activeSet, selectedKey, selectedColor

        |

        |     Find matching set and key

Save semantics (v0.8): adoption now saves the adopted combo itself (not the pre-adoption state) to history, then applies it. saveCombo's whole-array dedup is what handles a same-combo adoption — the prepended pill collapses against any existing visual duplicate, so no separate post-cleanup pass is needed (the old removeHistoryDuplicatesOfSlots() is gone).

Group adoption mirrors this: long-pressing a roster member (or tapping a strip pill while in a group) routes through groupContext.applyAdoptedComboInGroup(statusColor, paletteKey), which writes the group's statusOverride + per-group palette state and saveCombos the same adopted combo.

5.6 History Pill Restore INTERACTIONS

User taps history pill [idx]
  |
  v

  |

  |
  +-- if active context is a GROUP:
  |     applyAdoptedComboInGroup(combo.statusColor, combo.paletteKey)
  |       (writes the group's statusOverride + per-group paletteState; same
  |        path as long-press group adoption, sourced from the pill)
  |     return
  |
  +-- else (Direct): restore the live picker to this combo
        +-- state.sets[combo.activeSet].selectedKey   = combo.selectedKey

Changed since v0.7: restoring no longer snapshots/reshuffles history (the old "prepend the overwritten slot" + _lastCommittedCombo bookkeeping is gone) — a tap just restores. And a tap behaves differently per context: in Direct it restores the picker; in a group it applies the combo to that group's override.

6. Favorites Deduplication

The strip dedupes by visual identity so two combos that look the same don't both appear. With the slot model gone, this collapsed from four interacting mechanisms to one:

FunctionComparesUse
pillsLookSame(a, b) statusColor + surface2 Visual equality — only what the user sees (pill left/right colors). The single comparison used everywhere.
dedupeCombos(arr) — Walks the array keeping the first occurrence of each pillsLookSame group. Cleans both freshly-written and server-sourced arrays.

Every saveCombo(combo) prepends the incoming combo, runs dedupeCombos over the whole array (so an incoming duplicate collapses against any existing pill regardless of position), then caps at 8. A fast path skips the write entirely when the incoming combo already matches the head and the array has no deeper duplicates. prefs.syncFromServer runs the same dedupeCombos on arrays arriving from other devices.

Why visual-only (statusColor + surface2)? Two pills that render identically would be confusing to keep both, even if their underlying combo objects differ (e.g. a base-mode forest vs. a palette-mode forest can share a dot color). Dedup deliberately ignores paletteKey/selectedKey/activeSet and compares only the two colors a pill actually shows.

8. Call Canvas

When two mutual users enter a "call," they transition to a shared drawing canvas. The canvas persists between sessions for each unique pair of users.

8.1 Firebase Schema

canvases/
  {canvasId}/                        // sorted pair: e.g. "uid1_uid2"
    bg: string                       // canvas background (surface color)
    presence/
      {userId}: boolean              // true = on canvas, false = left
    strokes/
      {strokeId}/
        userId: string
        color: string                // hex
        thickness: number            // normalized 0–1
        tool: "pen"
        points: [[x,y], ...]         // normalized 0–1 coordinates
        timestamp: number

canvasId is derived from sorted user IDs: [uid1, uid2].sort().join('_') — ensures both users reference the same canvas regardless of who initiated.

8.2 Call & Canvas Flow

Entering Canvas

Caller swipes right on card
  → enterCallMode() — startCall(): writes calls/{caller} + calls/{callee}, card glows

Receiver sees glow, swipes right (answers)
  → answerCall(): sets answered=true on both calls/ mailboxes
  → enterCanvas(peerId, peerName, myUserId, myColor, peerColor, surface, onExit)
     → loadCanvas() — get existing strokes + bg
     → render strokes on <canvas>
     → watchStrokes() — listen for peer's new strokes (returns its unsub)
     → setCanvasPresence(true)
     → watchCanvasPresence() — detect peer leave/rejoin
     → build floating UI (header + toolbox)

Caller's own-call watcher (watchOwnCall on calls/{me}) sees answered=true
  → auto-enters canvas (same enterCanvas flow)

Exiting Canvas

User taps ‹ header → confirmation dialog → confirms
  → exitCanvas()
     → setCanvasPresence(false)
     → drains its watcher unsub list (strokes/presence/bg/drawing/clearRequest)
     → remove floating UI, show main UI
  → exitCallMode(myUserId)
     → endCall(myUserId, peerId) — clears both calls/ mailboxes (the side that
       hangs up writes the teardown; a peer-ended exit skips it, see note)

Peer (still on canvas):
  → presence watcher sees false → dims header, shows "partner left" dialog
  → if user calls back: presence goes true → dialog dismissed, header undims
  → if peer taps Done: exitCanvas() + exitCallMode()

Re-entry

After leaving canvas, if peer is still on canvas, their card keeps glowing (peer's calls/ mailbox still references you). Swiping right on the glowing card re-enters the canvas with one swipe — the existing receiver-answer code path handles it since isCallModeReceiver is true.

8.3 UI Components

The canvas screen is a full-screen fixed overlay (#canvas-screen.active). Main UI (header, strip, list) is hidden while canvas is active.

ElementPositionBehaviour

8.4 Drawing Engine

Drawing uses the HTML Canvas 2D API with pointer events.

Stroke Normalization

Points are stored as normalized 0–1 coordinates (x/canvasWidth, y/canvasHeight) so strokes render correctly on any screen size. Thickness is also normalized (multiplied by canvas width when rendering).

The canvas also supports a background-color picker (synced via watchCanvasBg), real-time mid-stroke preview to the peer (setDrawingState/watchDrawing), own-stroke undo (capped at 8), and clear-canvas with mutual agreement (setClearRequest/watchClearRequest) — all shipped since v0.7.

Drawing Flow

  • pointerdown — begin stroke, record first normalized point
  • pointermove — draw locally (incremental lineTo), append point
  • pointerup — render completed stroke locally, push to Firebase
  • Single taps (no pointermove) produce a dot rendered via renderStroke

Pen Colors

Colors come from getCanvasColors().penColors — unique statusColor values from the user's favorites history, padded up to 4 with default palette colors when the user has fewer. The user's current statusColor is the default pen and is prepended if not already in the list.

Key Communication Patterns

  • Custom events: palette-state-changed is dispatched by palette interactions; favorites-synced fires when a sibling device's favorites land via watchUserPrefs → prefs.syncFromServer. The favorites strip listens to favorites-synced and re-renders.
  • Direct imports: favorites.js imports switchSet / enterPaletteMode from palettes.js; following.js and groupContext.js import saveCombo / buildAdoptedCombo from favorites.js; me.js imports saveCombo / buildDirectCombo.
  • Firebase stream: Peer visibility is entirely through watchPresence. There is no direct communication between users' palette pickers — one user's setStatusColor/setPaletteKey writes are read by peers' updateFolloweeRow callbacks.
  • CSS variables as shared state: --my-status is read by both buildDirectCombo() (favorites) and the status dot styling (me.js). It is the source of truth for the active status color in the active set.
