Plaintext graduation phrase at rest in localStorage

js/graduationPhrase.js

The graduation phrase (an account-recovery credential) is persisted in plaintext in localStorage, keyed by uid. It is cleared on unlink, sign-out, and identity switch, and mirrors the pre-existing statusapp_identity posture — so it is residue-at-rest on a shared device only until teardown, and was judged not a diff-introduced vulnerability. Independently corroborated by the Opus VibeSec sweep (VS-1, observation-only, confidence 4/10): an XSS anywhere on the origin could lift the credential, but no XSS sink exists in this diff.

Suggested action: Decide whether the threat model includes shared/compromised devices; if so, consider session-only storage (re-reveal only within the post-graduation session) or encrypting at rest. Otherwise sign off as accepted (matches existing identity posture).

VS-1 detail: storeGraduatedPhrase() writes the plaintext secret recovery phrase to localStorage (key statusapp_grad_phrase_<uid>) so the drawer can re-reveal it after graduation and after a manual link (telegramSettings.js:143, graduation.js:51). localStorage is readable by any script running on the origin, so an XSS anywhere in the app would exfiltrate the account's only credential. This is a NEW expansion of that surface to Telegram accounts, but it deliberately mirrors the existing web posture (statusapp_identity already persists the web recovery code) and its lifetime is bounded: clearGraduatedPhrases() runs on unlink and sign-out, and it is keyed by derived uid so no cross-account read occurs. Reported only as a concrete, actionable defense-in-depth note, explicitly not a vulnerability. Exploit scenario: a hypothetical XSS on the app origin reads localStorage and lifts statusapp_grad_phrase_* / statusapp_identity, permanently compromising the account (the phrase is the sole recovery credential). No such XSS sink was found in this diff; the app consistently escapes user/Telegram-origin strings with escapeHtml or uses textContent. Recommendation: accept explicitly as consistent with the existing recovery-code model, or consider not persisting the phrase (re-reveal only within the single post-graduation session) so an XSS window cannot lift a long-lived credential. The existing unlink/sign-out clearing is good; keep it.
