KnockKnock · Telegram adaptation

"Use in Telegram" — one-tap link for existing web users

Onboard current web/PWA users onto the Telegram Mini App by carrying their existing account across in a single tap — no phrase re-typing, no new identity mechanics.

DRAFT — for review 2026-07-09 branch: claude/telegram-web-onboarding-2wl6cf base: t1r1jp @ 73cd010

§0What this is (and isn't)

A web user already has a phrase account — contacts, groups, prefs — and is signed in (auth.uid === userId). The goal is to let them adopt the Telegram Mini App for that same account in one tap, instead of the current manual path (open Mini App → drawer → "I have a secret phrase" → type the 4-word phrase → Link).

  • In scope: a one-time promo + a durable drawer entry in the web app; a server-minted single-use link token; auto-link on Mini-App arrival; and safe handling when the user already has a Telegram-only account with data.
  • Not in scope: new identity plumbing (reuses the existing linkTelegram routine), and account merge — the "no merge" boundary from the identity model stays uncrossed (see §4).

§2Architecture & data flow

Nothing in the identity model is invented. The redeem step calls the same performLink routine the manual drawer link uses — the only difference is the account uid is resolved from a token instead of from a typed phrase.

Why this is safe on credentials The phrase is never sent anywhere. The mint call is authenticated by request.auth.uid; the token is opaque, single-use, and short-lived. This is strictly stronger than putting the phrase in the deep link.

§3The edge case — user already has a Telegram-only account with data

When the Mini App boots, initData sign-in resolves to that Telegram's deterministic derived account. If the user had previously used the Mini App standalone, that account may already hold contacts and groups. Linking the web account expunges the derived account (linkTelegram → expungeDerivedAccount) — this is the identity model's deliberate "no merge" boundary. A silent auto-link would therefore destroy that data without warning.

On redeem, is the Telegram-derived account non-empty?
(counts read server-side from the same followers / following / groups nodes expunge reads)

✓ Empty → silent auto-link

0 contacts && 0 groups

The common case (fresh account, or opened once and never used). Link immediately, land in the web account, show the "✓ Linked" toast. Keeps the "quick action" promise.

⚠ Non-empty → confirm before replacing

≥1 contact || ≥1 group

Server returns {needsConfirm, counts} and does not link or consume the token. The Mini App shows a modal naming exactly what will be lost. Only an explicit confirm re-calls with confirm:true to perform the link.

The confirmation (non-empty branch)

Linking replaces this temporary Telegram account — its contacts and groups will be removed.

Link account Cancel

The confirm uses the existing linking-flow sentence (the showLinkScreen subtext) verbatim — it already spells out the data loss, so no new warning copy is invented. Two choices only: no graduate escape hatch. Cancel leaves the user on the Telegram account untouched (its token is not consumed and simply expires).

Enforcing the check server-side (not just client-side) means the destructive replace can never happen without the counts being computed and a confirm flag being present — robust even if a client is stale.

§4Server design functions/

  • Extract performLink(uid, tgUser, deps) from the body of linkTelegramHandler (the repoint + expunge-derived + prefs writes + mintToken). linkTelegramHandler keeps deriving uid from the phrase, then delegates — a pure extraction so the pinned link/unlink tests stay byte-identical (respects the "don't disturb expunge" landmine).
  • mintTelegramLinkTokenHandler — requires request.auth.uid; writes telegramLinkTokens/<token> = {uid, exp} via Admin SDK; returns {token}. Random 22-char base64url. A fresh token every call — the web CTA mints on each tap and never caches; an unredeemed token expires on its own (optionally the mint clears this uid's prior tokens to avoid buildup).
  • redeemTelegramLinkTokenHandler({initData, token, confirm}) — requireTelegramUser (verifies initData) · read token (reject missing/expired) · read the derived account's follower/following/group counts · if non-empty && !confirm → return {needsConfirm, counts} (token untouched) · else performLink + delete token + return {token: authToken}.
  • Wiring in functions/index.js — two new httpsOnCall exports mirroring linkTelegram, same makeTelegramAuthDeps().
  • Rules — telegramLinkTokens stays server-only (no client read/write in database.rules.json); both callables use the Admin SDK, so no rules relaxation.

§8Security notes

  • Token hijack race: the token sits in the t.me URL, so in principle it could be lifted from web-side history and redeemed by another Telegram first. Mitigation: ~5-min TTL + single-use + the legit redeem fires within seconds. Bounded, and strictly better than option A (phrase in URL).
  • No rules change, no migration — consistent with the F1 posture; the deploy still needs the A5 redeploy like the other branch-only Telegram functions.
  • Relink edge: opening a Telegram already linked to a different phrase account routes through linkTelegram's existing A→B relink branch (resets A's prefs, doesn't expunge A). Rare; handled by the reused routine.

§9Testing

  • functions (cd functions && npm test): mint (auth required, token shape/exp), redeem (happy path links + consumes token; expired/missing rejected; non-empty → needsConfirm without linking; confirm:true links + expunges), and performLink extraction leaves the existing link/unlink suites byte-identical.
  • web (npx jest): banner + card gating/suppression, dismissal persistence, deep-link build, mint call wiring; boot dispatcher lk_ branch + confirm re-call.
  • rules (npm run test:rules): telegramLinkTokens denies all client access.
  • Gate: the on-device walkthrough (web tap → Mini App → linked; and the non-empty replace-confirm path) is the acceptance gate — green suites are necessary, not sufficient.

§10Resolved

  • Graduate escape hatch — no. Two-choice confirm.
  • Token — 5-min TTL, single-use, lk_ prefix, fresh mint on every tap.
  • Confirm copy — the existing linking-flow sentence, verbatim.
