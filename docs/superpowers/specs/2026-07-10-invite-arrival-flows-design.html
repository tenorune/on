KnockKnock invite arrivals — holistic in-app-browser design

Issue #283 (duplicate account from Telegram's in-app browser) · folds in #265 (/invite route) · 2026-07-10 · branch claude/telegram-duplicate-account-bug-s9i7bs · repo copy: docs/superpowers/specs/2026-07-10-invite-arrival-flows-design.html (+ companion .md)

Decisions Q1–Q7 and amendments A1–A4 from the 2026-07-10 brainstorm. Wireframes are lo-fi on purpose — copy is draft-grade, tuned on device. Supersedes the same-day markdown draft; extends spec 2026-07-05 (§9 gap) and leaves spec 2026-07-07 (interstitial) as-built except the one addition noted.

Chosen treatment (Q7 = C+A)

Group invites come along for free (redemption already handles scope). Implementation note: the input’s maxlength="6" must lift to admit a pasted URL.
  • Landing’s third door. Config #1 gains a quiet line under the CTA pair: “Already have the app installed? Copy the invite and paste it under Add a person.” — with a one-tap copy button. Deliberately tertiary: only installed users need it.

Normative specification

The rules the implementation must satisfy. File references are to the current tree.

N1 · Shared link change (A1)

  • buildInviteUrl(token) (js/invites.js:51) returns ${APP_URL_BASE}/invite?i=${token}. It is the single construction point; all callers (invite modal, mycode, groupContext) build the URL from the token at display time — nothing persists the URL, so no migration.
  • Legacy/copied /?i= links keep working via the boot gate (N3).

N2 · Routing (firebase.json)

  • Additive rewrite above the ** catch-all: { "source": "/invite", "destination": "/about.html" }. Same physical page as /about; query strings pass through (standard Firebase behavior — walkthrough-verify).
  • /invite is root-level, so the page’s relative asset URLs resolve unchanged.

N3 · Boot gate (js/app.js main())

  • Sits immediately after extractInviteTokenFromUrl (app.js:564), before ensureIdentity and any Firebase work. Evaluates the decision tree above in order; on a redirect/auto-hop outcome it calls location.replace(…) and returns from main().
  • Predicates: isTelegramContext() (existing) · ?stay=1 (URLSearchParams) · loadIdentity()/isStandalone() (existing) · isTelegramInAppBrowser() (new, N7) + deep link configured · isInAppBrowser() (existing) · isIos() (newly exported, N7) + telegramSharingEnabled() (existing).
  • Auto-hop target: buildTelegramInviteLink(token) (js/inviteFlow.js:21). Unconfigured link → falls through to the in-app-browser redirect row.
  • Phase 2 adds the tokenless branch: fresh + isInAppBrowser() → location.replace('/about'). iOS-undetected tokenless boots never redirect.
  • cleanInviteParamFromUrl (app.js:555) additionally deletes stay.
  • stay=1 boots skip showInAppBrowserRedirect (phase 1); the panel and its call site are removed in phase 2 (Q6=A).

N4 · Page behavior (about.html serving /about + /invite)

  • Pages never redirect and never auto-hop for fresh visitors — they are the mint-free choice surface. One exception (C1): identity-aware pass-through — on config #1 only, when localStorage.statusapp_identity exists (js/identity.js:4; same-origin, the template’s theme script already reads app localStorage), continue immediately to /?i=TOKEN&stay=1 in the same window. With an identity there is no mint risk. Config #2 (/about?i=) deliberately does not pass through — it is a reading page.
  • Config selection is by location.pathname — the first path-sensitive behavior in the about scripts; applies to the about page only. /invite + valid token → config #1; /about + valid token → config #2; no/invalid token → plain page (tokenless /invite falls back to plain).
  • Token validity: /^[A-Za-z0-9_-]{1,64}$/ — the shape about-invite.js:11 and about-cta.js:22 already use.
  • Invite block (both configs): static headline; the existing #about-invite-framing element moves inside unchanged (about-invite.js untouched — it upgrades the line when the preview resolves); equal-weight CTA pair (Q3=C): “Open in Telegram” = data-telegram-link + '?startapp=' + token, “Continue in browser” = data-open-app break-out; tertiary installed-app line + one-tap “Copy invite” (copies the canonical /invite?i=TOKEN URL). Clipboard failure (common in webviews) falls back to the URL as selectable text (C7). On iOS the installed-app door is visually promoted — implement-and-evaluate (C5).
  • One set of doors: while the invite block is visible, the intro hides both of its CTAs (“Open KnockKnock →” and the standing bare Telegram CTA).
  • Config #1 collapse (v1): everything below the logo folds behind one expander (“More about KnockKnock”) — except the intro’s first sentence, which stays visible so a stranger has minimum context to choose a door (C4). Script-off fallback = fully expanded page; nothing is ever unreachable. Finer split: followup.
  • Standing bare Telegram CTA (A3): on token-less pages, the intro shows “Open in Telegram” → bare t.me/<bot>/app beside “Open KnockKnock →”.
  • Fail-closed: every Telegram CTA renders hidden and only unhides when data-telegram-link is non-empty and not an unsubstituted __…__ placeholder (mirrors about-invite.js:15).
  • Loop guard: about-cta.js appends stay=1 to every link it rewrites, token or not (C2) — a tokenless browser_fallback_url re-entering the webview would otherwise loop through the phase-2 bare redirect. iOS x-safari-https, Android intent:// incl. fallback, desktop plain; the x-safari break-out itself is unchanged, pre-existing behavior.
  • New logic lives in a new single-purpose classic script (js/about-telegram.js, mirroring about-invite.js’s pattern); about-cta.js changes only for stay.

N5 · Build substitution (scripts/build.js)

  • renderAbout() gains __TELEGRAM_APP_LINK__, substituted as TELEGRAM_ENABLED && env.TELEGRAM_APP_LINK || ''.
  • Wrinkle: TELEGRAM_ENABLED is a hardcoded const in js/features.js (ESM), not an env var — build.js (CJS) reads it from the source text via /export const TELEGRAM_ENABLED = (true|false)/. Keeps features.js the single source of truth so a post-merge build with the flag off cannot advertise a dead bot link, and the page can never disagree with telegramSharingEnabled().

N6 · In-app invite redemption — the unified “Redeem an invite” form (U1 + preview)

A universal affordance for every signed-in user on every platform — paste any invite and redeem it in place. The installed-PWA recipient (Q7 = C+A) is its most load-bearing consumer, not its only one.

  • One form, content-detected mode — no tabs. Today’s single button and form stay (index.template.html #add-person-form, js/following.js). Copy (operator-set): the button reads “Redeem an invite” (was “Add a person”); the field label reads “Code or invite link”; the placeholder covers both shapes (e.g. XK7P2M or an invite link — final wording on device). The input accepts anything (maxlength="6" lifts) and the form adapts to what it holds.
  • Code mode (6-char shape): today’s behavior — Name field, “Follow” button, same validation. The first-run demoted relabel (js/firstRun.js:62, “Add by code”) is removed — with the rename, “Redeem an invite” makes sense in every state; the demoted styling toggle stays.
  • Invite mode (a URL with an i= param, a t.me/…?startapp=TOKEN link (C6), or a raw 22-char base64url token /^[A-Za-z0-9_-]{22}$/): the Name field hides, the button reads “Redeem invite”, and a status line under the input announces the detection. resolveInvitePreview (unauthenticated, already exists) upgrades the line to “You’ll follow Ana” / “You’ll join ‘Hikers’” — fail-soft: on preview failure the line stays “Invite link detected” and submit still redeems.
  • Anything else on submit → inline error: “That doesn’t look like a code or an invite link.” Redemption reuses the existing pipeline (attemptRedeemFromUrl + handleInviteRedemptionResult) — personal and group invites both work.
  • Followup (not v1): keep the Name field in invite mode as a local-label override (U3) — needs a post-redeem rename; label plumbing exists in following.js.
  • C-side: desktop Telegram routes /?i= into the installed app (operator-observed); /invite?i= expected to follow — walkthrough. Android intent://→WebAPK hand-off: walkthrough item. A manifest launch_handler/capture tune-up is a possible followup, not in scope.

N7 · Detection helpers (js/installGuidance.js)

  • New export function isTelegramInAppBrowser() = /Telegram/.test(ua()) — an Android-only positive signal (already a substring of isInAppBrowser()’s pattern, line 36); iOS Telegram is indistinguishable from Safari and correctness never depends on this helper.
  • Export the existing module-private isIos() (line 20; already handles iPadOS-as-Macintosh).

N8 · Mini App interstitial (A4, on top of spec 2026-07-07 as-built)

  • “What is KnockKnock?” link → /invite?i=TOKEN, shown only when isNew (the flag already passed to showInterstitial, js/telegramFirstRun.js:63). Opens within Telegram so the user returns to the interstitial. The page’s loop-back “Open in Telegram” CTA is accepted for v1; a variant is a followup.

Phasing

  • Phase 1 — shared links become /invite?i= (N1); boot decision tree for /?i= (N3); config #1/#2 page work incl. identity pass-through (N4); standing /about Telegram CTA; build gate (N5); unified add/redeem form + landing copy door (N6); interstitial info link (N8); unconditional stay=1 loop guard; panel skipped on stay=1.
  • Phase 2 — after the phase-1 on-device walkthrough: bare-arrival redirect for detected in-app browsers (F8) + panel retirement.
  • Phase 3 (Q8=C) — after the phase-2 walkthrough, own evaluation gate: the tokenless redirect widens to all fresh boots (closes the iOS bare blind spot; costs the funnel one hop + the iOS prompt — evaluate on device before keeping). Planning consequence: desktop-tokenless data-open-app links must then also rewrite to /?stay=1, or the landing bounces desktop visitors back.
  • Done = the operator’s on-device walkthrough, not green suites.
