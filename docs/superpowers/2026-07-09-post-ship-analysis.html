KnockKnock · Telegram adaptation

Post-ship analysis — gaps, opportunities & code health

Two independent read-only reviews of the shipped Telegram adaptation: a product/UX gap-and-opportunity walk of the user journeys, and an inefficiency/redundancy review of the production diff. All findings cite the code they were observed in; nothing here has been changed yet.

2026-07-09 branch claude/telegram-adaptation-shipped-otg0ma @ 52971b9 diff base origin/dev (merge-base = dev tip) 122 files · +26,781 / −299 suites at analysis time: web 1535 · functions 351 · rules 71

1Scope, method & how to read this

Method. Two parallel, isolated review passes over the same tree (no shared state, no edits):

  • Workstream U (product/UX) — read docs/HANDOFF.md §45–§48 and docs/telegram-setup.md for intent, then walked six journeys end-to-end in code (onramp; web→Telegram link incl. both confirm branches; graduation→recovery; channel switch; unlink/relink; error paths). Findings grouped under three lenses: unmet user needs, cross-surface inconsistencies, delight opportunities.
  • Workstream C (code health) — reviewed the ~40 production files in git diff origin/dev..HEAD for redundancy, inefficiency, dead code and structural smells. Explicitly briefed on the two intentional cross-runtime duplications (three-reader channel predicate; time formatters) so they were audited for guard integrity, not flagged as defects.

Metadata per finding. Severity/value (reviewer's impact call) · Evidence (OBSERVED = behavior read directly in code, with refs; INFERRED = likely but not fully verified by reading) · Effort (S ≈ <½ day, M ≈ ½–2 days, L = larger/design work) · Surfaces touched · Deploy (client-only vs needs a functions deploy) · Cluster (synthesis cross-reference, §5–§6).

Deploy dependency Anything marked functions stacks onto the maintainer's pending t1r1jp→dev→main merge + A5 redeploy (docs/telegram-setup.md A5): a dev push wipes branch-only Telegram functions until the redeploy, and the server-gated confirm branches can only be walked on device after it. Client-only items have no such dependency.
Already-known items — excluded as discoveries Issue #286 (invite management from Telegram, open) · #288 (rules follow-up, maintainer's call) · unredeemed telegramLinkTokens expiry-checked on read, not swept (accepted) · onramp-linked accounts have no local phrase vault by design. Findings below may build on these but do not re-report them.

U1.1Forwarded "Use in Telegram" link silently links a stranger's Telegram to your account
HighObservedForwarding likelihood inferredCluster A
User moment
The minted t.me/<bot>?startapp=lk_… URL is an ordinary Telegram link — forwardable, or opened on the wrong account by multi-account users.
Evidence
Token bound only to the minter's uid (functions/telegram-auth.js:193-199); redemption accepts whatever Telegram identity presents it, and when that Telegram's derived account is empty (contacts === 0 && groups === 0) there is no confirm at all — straight to performLink (functions/telegram-auth.js:226-240). Direction
Always show a lightweight confirm on redeem naming the account being linked ("Link this Telegram to KnockKnock account ⟨code⟩?"), even for empty derived accounts — one tap for the owner, a decisive tell for anyone else.

3Workstream C — code inefficiencies & redundancies

C1Every web boot gates on a telegram.org fetch
Value 1inefficiency · boot pathCluster D
Evidence

5Synthesis — clusters

Where the two workstreams point at the same code, fixing together beats fixing piecemeal. Every finding maps to exactly one primary cluster (a few have a secondary); the full matrix in §6 covers all items.

  • A · telegram-auth.js combined pass — U1.1 (redeem confirm), U1.2 (web unlink), U1.3 (channel rerouting) land in the same file as C2 (twin movers) and C8 (double read). One coherent server-side change-set, one test-suite touch, one deploy. Gate: check #287's adjudication of U1.1 first.
  • B · Replace-confirm copy — U2.1 (conditional, count-specific warning) and C6 (duplicated warning string) are the same sentence: making it conditional and count-driven naturally consolidates it behind one constant/helper.
  • C · Channel honesty & the predicate — U1.3's channel handling is exactly the code the three-reader predicate protects; C10's shared vector fixture and C3(a)'s read-timing change should land with (or before) it so the invariant is machine-guarded while it's being touched.
  • D · Client-only quick wins (no functions deploy) — U1.4, U1.5, U1.7, U1.8, U2.2, U2.3, U2.4, U3.1, U3.3, C1, C4, C9. All small, independent, and shippable before the maintainer's A5 redeploy.
  • E · Bot-surface polish pass (one functions deploy) — U1.6, U2.5, U2.6, U2.7, U3.2, C3(b)(c), C5. All inside functions/telegram.js/notifier.js; natural single change-set.
  • F · Invariant guards — C7 (key lists), C10 (three guard holes), T-1 (shared mock factory). No behavior change; pure future-drift insurance.
